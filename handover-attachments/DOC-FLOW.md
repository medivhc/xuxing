# 文档流转与抽查协议（2026-10-24 用户立意，协调者落档）

## 原则
文档类产物（评审报告、盘点、契约修订、设计稿）在执行器之间**以文件流转**，不经协调者在聊天里全量摄入再复述。协调者只读结构化头部 + 按协议抽查，节省 token 且保留唯一正本。

## 文件头（每份流转文档必须带）
```
artifact: <类型，如 review/fix-report/inventory>
based_on: <代码基线 commit 短哈希>
sha256: <正文哈希，回收时由协调者复算校验>
verdict: <结论，如 CHANGES_REQUESTED / APPROVED>
counts: <条目数按级别，如 BLOCKER 2 / MAJOR 7 / MINOR 8>
producer: <模型 + 会话 id>
```

## 流转规则
1. 产物回收走 API 逐字取回（Qoder events/artifacts 接口），禁止页面文本抓取大文档；回收后先验 sha256 与条数，再入 `results/` 或仓库。
2. 下游任务书只给**文件路径 + 必须逐项回应的条目清单**，并要求执行方在报告中引用条目编号对账，不许"已阅，已改"式含糊交付。
3. 同一事实只有一个正本文件；修订产生新版本文件（日期/轮次入文件名），旧版归档不删。

## 抽查协议（协调者验收时）
- **全查**：所有 BLOCKER 级条目逐字核对（原文位置、修复落点、证据）。
- **抽查**：MAJOR/MINOR 随机抽 ≥30%，含至少一条"看起来最容易糊弄过去"的。
- **机器校验**：条数与头部 counts 对齐；测试数字与 CI/patch 文件交叉验证；grep 关键标记（如 NX_PHASE_COMPLETE、结论词）。
- **升级**：抽查发现一处不实时，整份升为全查。

## 适用边界
- 适用：评审、盘点、文档修订、测试报告等文档类流转。
- 不适用：多份结论冲突需裁决综合、产品判断、用户待拍板事项——这类协调者必须读关键原文，只免"全量搬运"，不免"关键深读"。
