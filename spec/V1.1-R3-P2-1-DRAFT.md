## 1. 范围、依据与不在范围

### 1.1 问题陈述

`K0-CONTRACT-REVIEW-R3.md` §四第 1 条与候选清单 R3-P2-1 指出：REQ-RUN-4 的租约过期分界按（是否已启动 × 副作用级 × 外部副作用调用记录）有多条支路，而 §8.2 只有两条用例——C1（已启动且满足 indeterminate 条件 → indeterminate → 对账）与 C1b（未启动 → 回 `queued`）。**行为本身已在 REQ-RUN-4 写死、可判定，缺的是验收用例而非语义**，故列 P2、不阻塞冻结。

本文的产出是：把该分界的**全部组合穷举成表**（§2.2），对 C1/C1b 未覆盖的支路按 §8.2 既有格式写草案用例（§3），逐条标注与 C1/C1b 的区别点，并把拿不准的部分标为「待裁决」并写明疑问（§3.5），最后给出无冲突声明（§5）。

## 2. 分界因子与支路穷举

### 2.1 三个判定因子（按 REQ-RUN-4 原文）

REQ-RUN-4 写死判定只依据三项，本文即以此三项为穷举维度：

1. **是否已启动**：以 `RunStarted` 事件是否存在为准（REQ-RUN-4 原文括注「未启动（无 `RunStarted`）」）。
2. **`side_effect_level`**：按规则只区分两组——`{L0, L1}` 与 `{L2, L3}`（规则对组内两个取值不作区分）。
3. **外部副作用工具调用记录**：有 / 无。记录的具体载体在 v1.0 未定义（见 Q1），本文的用例只以「记录存在 / 不存在」这一抽象前置表述，**不指定表名、事件类型或写入路径**。

### 2.2 八条组合（2 × 2 × 2）

| 支路 | 已启动（有 `RunStarted`） | `side_effect_level` | 外部调用记录 | v1.0 字面判定 | §8.2 现有覆盖 | 本文草案用例 |
|---|---|---|---|---|---|---|
| B1 | 否 | {L0, L1} | 无 | 回 `queued` | C1b（未标注另两个因子） | 不新增（见 B0 变体说明） |
| B2 | 否 | {L0, L1} | 有 | 回 `queued` | C1b 未标注因子 | C1b-B0 变体 |
| B3 | 否 | {L2, L3} | 无 | 回 `queued` | C1b 未标注因子 | C1b-B0 变体 |
| B4 | 否 | {L2, L3} | 有 | 回 `queued` | C1b 未标注因子 | C1b-B0 变体 |
| B5 | 是 | {L0, L1} | 无 | `failed`（原因 `lease_expired`） | **无** | **C1c** |
| B6 | 是 | {L0, L1} | 有 | `indeterminate` | C1 前置为整条析取式，未区分 | **C1e（待裁决）** |
| B7 | 是 | {L2, L3} | 无 | `indeterminate` | C1 未证明「等级单独充分」 | **C1f** |
| B8 | 是 | {L2, L3} | 有 | `indeterminate` | C1 可能恰为此组合 | 不单列（理由见 §2.3） |

支路计数：**8 条组合**。其中「未启动」4 条（B1–B4）在 v1.0 下的判定收敛为同一结果（第一支只以「无 `RunStarted`」为条件）；「已启动」4 条（B5–B8）按副作用因子分为 `failed` 1 条（B5）与 `indeterminate` 3 条（B6–B8）。

### 2.3 C1 / C1b 的既有覆盖边界与缺口

1. **C1b 只覆盖「未启动」这一侧的一个代表组合**，其文未标注 `side_effect_level` 与「外部调用记录」两个因子。按 REQ-RUN-4 第一支的字面，这两个因子在未启动时**不参与判定**，因此 B2–B4 与 B1 同判定；差别仅在「是否显式验证因子被忽略」。
2. **C1 的前置条件把整条析取式（`side_effect_level ∈ {L2, L3}` 或已有外部副作用调用记录）写入**，因此 C1 通过**不能**证明以下两件事中的任何一件：
   - 「记录这一侧单独充分」——即 B6（L0/L1 且有记录）也应 `indeterminate`；
   - 「等级这一侧单独充分」——即 B7（L2/L3 且无记录）也应 `indeterminate`。
   C1 只能证明「至少一侧成立时 → indeterminate」，无法排除实现把析取误读为合取（两条同时成立才 indeterminate）。
3. **B5（已启动、L0/L1、无记录 → `failed(lease_expired)`）完全无用例覆盖**，这正是候选条目点名的组合，也是 R3 评审建议补 C1c 的对象。
4. **B8 不单列**：一旦 C1e（记录单独充分）与 C1f（等级单独充分）各自成立，B8 只是两侧同时成立，判定不变；单列不增加判别力。此判断不引入新语义，仅用于控制用例数量。

## 3. 支路用例草案（按 §8.2 格式：给定条件 → 期望判定/状态 → 依据）

以下每条用例均沿用 §8.2 C1/C1b 的书写结构与断言粒度，**只把 REQ-RUN-4 已写死的判定断言化**，不新增状态、事件类型或判定因子。

### 3.1 C1c（已启动 · `{L0, L1}` · 无外部调用记录 → `failed(lease_expired)`）

**给定条件**

1. Task T 有 active Assignment；Run R（`run_kind=executor`）经 Scheduler 派发，事件序列 `RunCreated → RunQueued → RunLeased` 已入账，`lease_expires_at` 已设（REQ-RUN-1）。
2. Executor 回报 `RunStarted`（R 进入 `running`）并按 REQ-RUN-1 续约心跳；`side_effect_level=L0`。
3. 租约过期判定时点前，**不存在**任何外部副作用工具调用记录（载体见 Q1，本文只作抽象前置）。
4. 杀 Executor 进程 → 心跳停止 → 租约过期，内核执行 REQ-RUN-4 判定。

**期望判定/状态**

1. R → `failed`，原因为 `lease_expired`（`RunFailed` 入账）。
2. **不进入 `indeterminate`**：事件流中无 `RunIndeterminate`、无 `RunReconciled`；不走 REQ-RUN-3 对账（依 §4 派生规则反向断言）。
3. REQ-RUN-2 不生效（该条只约束 `indeterminate` 在对账完成前的情形）：内核可为 T 新建 Run R'（新 id、新 `idempotency_key`，INV-4），不因本 Run 阻塞。
4. 迁移合法性只落在 §3.2 的 `leased→failed` 与 `running→failed` 两行；判定只依据（已启动、副作用级、记录）三项，不采信 Executor 自述。

**依据**：REQ-RUN-4 第二支；§3.2 迁移矩阵；INV-4；REQ-RUN-2（反向）；§4 派生规则声明。

**与 C1 / C1b 的区别点**

- 对 C1：C1 的前置是「`L2/L3` 或已有记录」，终态路径是 `indeterminate → 对账 → failed(reconciled_not_executed)`；C1c 的终态原因不同（`lease_expired`）、无对账、无 REQ-RUN-2 阻塞期。C1 无法覆盖本支路，因为它的前置排除了「L0/L1 且无记录」。
- 对 C1b：C1b 无 `RunStarted`（未启动）、回 `queued`、不达终态；C1c 有 `RunStarted`（已启动）、达 `failed` 终态。

**备注**

- `side_effect_level=L1` 以同一用例参数化重跑，其余断言逐项相同：REQ-RUN-4 第二支把 L0/L1 并列，v1.0 未给二者不同处置，草案不发明区分。
- 断言 3 中的「新 Run 派发成功」沿用 C1 的既有断言口径，不新增 Task 迁移规则；其前置空白见 Q5。

### 3.2 C1e（已启动 · `{L0, L1}` · 有外部调用记录 → `indeterminate`）· **待裁决**

**给定条件**

1. 同 C1c 的条件 1–2，`side_effect_level=L0`。
2. 租约过期判定时点前，**已存在**至少一条外部副作用工具调用记录（记录如何产生、以何形态被内核读取见 Q1；本草案不指定载体）。
3. 杀 Executor 进程 → 租约过期。

**期望判定/状态（按 v1.0 字面）**

1. R → `indeterminate`（`RunIndeterminate` 入账）：REQ-RUN-4 第三支为析取式，「已有外部副作用调用记录」一侧单独成立即足以触发。
2. 进入 REQ-RUN-3 对账；对账完成前，同一 Task 不得派发同契约范围的新 Run（REQ-RUN-2）。
3. 对账的具体结论分支不在此断言（C1 已覆盖「未执行 → failed(reconciled_not_executed)」路径）。

**依据**：REQ-RUN-4 第三支；REQ-RUN-2；REQ-RUN-3；§3.2 矩阵。

**与 C1 / C1b 的区别点**

- 对 C1：C1 的前置把整条析取式写入，因此 C1 通过无法证明「记录一侧单独充分」；C1e 专门钉住这一侧，并与 C1f 一起排除「析取被误实现为合取」。
- 对 C1b：C1b 是未启动分支，与副作用记录无关；C1e 是已启动分支，记录存在与否直接改变判定。

**待裁决（本支路整条标「待裁决」，不对 v1.0 作补充判定）**

- **Q3（可达性）**：v1.0 §1.1 只声明「副作用分级：L0/L1 完整实现」并列出 L2/L3 的放行边界，**未定义 L0–L3 各自的语义**。因此「`side_effect_level=L0` 且存在外部副作用工具调用记录」这一组合**是否可构造**无法从 v1.0 判定：
  - 若 L0 的语义是「无任何副作用」，则本组合为空集，本用例不成立，B6 只剩 L1 一侧；
  - 若副作用级与「外部调用记录」正交（记录可出现在任意等级），则本组合可构造，字面判定为 `indeterminate`。
  - 疑问（请 v1.1 裁决）：是否给出 L0–L3 的语义定义，或明确声明「副作用级与外部调用记录正交、任意等级均可能出现记录」？
- 在 Q3 裁决前，本用例**不列入退出门必需项**；其断言 1–2 的内容仍以 v1.0 字面为准，不因标「待裁决」而被推翻。

### 3.3 C1f（已启动 · `{L2, L3}` · 无外部调用记录 → `indeterminate`）

**给定条件**

1. 同 C1c 的条件 1–2，`side_effect_level=L2`（另以 `L3` 参数化重跑一遍）。
2. 租约过期判定时点前，**不存在**任何外部副作用工具调用记录。
3. 杀 Executor 进程 → 租约过期。

**期望判定/状态**

1. R → `indeterminate`（`RunIndeterminate` 入账）：REQ-RUN-4 第三支中「`side_effect_level ∈ {L2, L3}`」一侧单独成立即足以触发，不要求同时存在调用记录。
2. 进入 REQ-RUN-3 对账；对账完成前禁止派发同契约范围的新 Run（REQ-RUN-2）。
3. 对账结论分支不在本用例断言（由 C1 覆盖）。

**依据**：REQ-RUN-4 第三支；REQ-RUN-2；REQ-RUN-3；§3.2 矩阵。

**与 C1 / C1b 的区别点**

- 对 C1：C1 无法区分「析取」与「合取」；C1f 以「无记录」这一显式前置证明等级一侧单独充分，是判定析取语义的关键用例。
- 对 C1b：C1b 未启动；C1f 已启动，且副作用级为高等级。

**备注**：C1f 与 C1e 均通过，才完整证明 REQ-RUN-4 第三支是析取（OR）而非合取（AND）；这也是 B8 不单列的理由（§2.3 第 4 点）。

### 3.4 C1b-B0 变体（未启动 · 任意副作用级 · 任意记录 → 回 `queued`）

**给定条件**

1. Run R 仅被领取（`RunCreated → RunQueued → RunLeased` 已入账，`lease_expires_at` 已设），**无 `RunStarted`**。
2. `side_effect_level=L3`，且判定时点前**已存在**外部副作用工具调用记录（构造方式同 Q1）。
3. Executor 进程被杀 → 租约过期。

**期望判定/状态**

1. R 回 `queued`（`leased→queued`）：REQ-RUN-4 第一支的条件只含「无 `RunStarted`」，副作用级与记录均不参与判定。
2. 不进 `indeterminate`、不走 REQ-RUN-3；随后可被重新领取并正常启动（与 C1b 相同）。

**依据**：REQ-RUN-4 第一支；§3.2 `leased→queued`；REQ-RUN-3（反向）。

**与 C1 / C1b 的区别点**

- 对 C1b：断言等价，区别只在**显式把副作用级设为最高、并构造记录存在**，用以验证这两个因子在未启动分支被忽略。C1b 未标注这两个因子，因此其通过不能排除「实现按副作用级提前分流」的错误。
- 对 C1：C1 已启动，本变体未启动，两者是分界的对立两侧。

**备注**：本变体属**冗余确认**（v1.0 判定与 C1b 完全一致）。是否作为独立用例列入 §8.2、或仅以注文并入 C1b，由 v1.1 裁决；本文建议至少以注文形式保留「未启动分支不看副作用因子」这一结论。

## 4. 与 C1/C1b 的区别点汇总

| 草案用例 | C1 已覆盖的部分 | C1b 已覆盖的部分 | 本用例新增的判别力 |
|---|---|---|---|

### 5.2 如实列出的字面缺口与表述张力（不掩盖）

**结论先行**：本草案未发现任何一条用例要求与 v1.0 已写死判定**相反**的结果；以下各项均为「v1.0 未写」型缺口或「表述精度」问题，不是判定冲突：
