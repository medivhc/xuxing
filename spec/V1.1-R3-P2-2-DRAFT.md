## 0. 核心结论（摘要）

空判据集**既非普遍合法、也非普遍非法**，合法性取决于任务类型；两条边界同时成立：

1. **Agent 任务：空判据集合法性 = 非法**。依据 REQ-TC-1"指派给 Agent Executor 的 Task 必须有结构化 `acceptance_criteria`（至少一条可判定条目）与 `expected_outputs`"，空集在定义/契约换版/指派/派发四个时点均应被拒绝（拒绝点与错误口径见 §3.1）。
2. **人工任务：空判据集合法性 = 合法**（REQ-TC-1"人工执行的 Task 允许仅文本契约"）。此时 REQ-ACC-2 的 verdict 一致性校验与覆盖完整性校验**真空成立属预期行为**，不是缺陷；但 **verdict 必须由人显式给出**，内核不得从空集推导出任何 verdict，尤其不得自动判 `accepted`（见 §3.2）。
3. **判别依据只用冻结版既有字段**：当前 active `Assignment.actor_kind`（`human|agent`）与执行期 `Run.run_kind`（`executor|human_light`）。不以标题、描述、`assignee_hint`、Proposer 自述或任何新造字段判别（见 §2）。

## 1. 问题陈述与既有口径

### 1.1 空集使一致性校验失去判别力

REQ-ACC-2 的顶层 `verdict` 一致性规则为三分支：**全部 passed（或 not_applicable）→ accepted；全部 failed → rejected；其余混合 → partially_accepted**。

当 `criterion_results[]` 为空时，上述三个前件同时**真空成立**：既满足"全部 passed"，也满足"全部 failed"，且不满足"其余混合"。于是：

- 一致性校验无法唯一确定顶层 `verdict`，等价于对任意 `verdict` 都不产生约束（R3-P2-2 所指"恒真"）；
- 若实现直接按"全部 passed → accepted"的字面顺序套用，还可能把空集**误判为 accepted**，这正是不容发生的推论。

同时，"覆盖完整性"（契约全部 `criterion_ref` 必须出现在 `criterion_results`）与"继承锁定"两项校验在契约与结果**都为空**时也是真空成立——结果是"没有可校验项"，而非"校验通过了一项结论"。

### 1.2 两处既有口径的边界

- REQ-TC-1 只对 **Agent Executor** 要求"至少一条可判定判据 + `expected_outputs`"，对人工任务明确允许"仅文本契约"；它写死的执行后果是"**否则 Scheduler 不得派发**"。
- §3.1 `captured → defined` 另写"**指派 Agent 时**另须满足 REQ-TC-1"。
- v1.0 全文**未定义**：空判据集下人工任务的验收应如何入账、`verdict` 由谁给出、Agent 任务的空集应在哪一入口被拒绝、拒绝的错误口径是什么。本文只补这一段空白。

### 1.3 本文对"空判据集"的界定

本文所称空判据集指：`acceptance_criteria` **缺失、为 `null` 或为空数组 `[]`**。

判据条目存在但缺 `criterion_ref`、`criterion_ref` 为空串或重复，属**条目形状/schema 错误**，走既有 schema 校验，不在本文裁定范围（见 §5 待裁决 Q7）。

## 2. 人工任务与 Agent 任务的判别依据（全部引用 v1.0，不新造概念）

| 判别依据 | 冻结出处 | v1.0 原文要点 | 本文用法 |
|---|---|---|---|
| `Assignment.actor_kind: human\|agent` | v1.0 §2.4 | 指派与权限分离；同一 Task 至多一个 active Assignment（INV-14，§5.2） | **定义/契约/指派时点的权威判别字段**：取该 Task 当前 active Assignment 的 `actor_kind` |
| `ActorProfile.actor_kind: human\|agent` + `active` | v1.0 §2.4、REQ-SCH-4 | 未在册或 `active=false` 的 actor 不得被指派 | 用于核对被指派 actor 的在册身份；不引入新的任务类型概念 |
| `Run.run_kind: executor\|human_light` | v1.0 §2.4、§5.7 | `executor` 走 Agent 适配器；`human_light` 为人类执行尝试 | **执行/派发时点的兜底判别**：派发 `executor` Run 即 Agent 执行路径 |
| `TaskContract.acceptance_criteria[]`（每条带稳定 `criterion_ref`） | v1.0 §2.2 | 被 Run 引用后不可变（INV-5） | 判定"是否为空集"的对象，取当前 `contract_rev` |
| `TaskContract.expected_outputs` | v1.0 §2.2、REQ-TC-1 | Agent 任务与判据同句要求 | 仅作同句引用；本文不单独加严（Q7） |
| `assignee_hint?` | v1.0 §2.2 | 仅字段存在，无判定语义 | **明确不得作为判别依据**（非权威、可缺失） |
| REQ-ACC-2 | v1.0 §2.6 | actor 分离 + 逐判据结果 + 顶层一致 + 覆盖完整性 + 继承锁定 | 非空判据集沿用；空集按其空白处理 |
| `Acceptance.acceptor_kind` / `verdict` / `criterion_results[]` | v1.0 §2.6 | 验收记录形状 | 空集人工裁决的入账资格判定 |
| REQ-ACC-1 / REQ-ACC-3 | v1.0 §2.6 | Acceptance 跨 rev 有效；按最新有效 Acceptance 重算 lifecycle | 换版与重算口径不变 |

**判别规则（草案条文，D-0）**：

1. 定义、契约换版、指派三个时点，以该 Task **当前 active Assignment** 的 `actor_kind` 判别；无 active Assignment 时**不预判**任务类型，也不以"将来可能指派 Agent"为由拒绝人工任务的空契约定稿。
2. 派发时点，以即将创建的 `Run.run_kind` 判别：`run_kind=executor` 即 Agent 执行路径，适用 REQ-TC-1；`run_kind=human_light` 即人工执行路径。
3. 同一 Task 从人工改派为 Agent 时，任务类型随 active Assignment 变更；空判据集任务不得完成该改派（§3.1）。
4. 禁止以 `title`/`description` 文本、`assignee_hint`、Proposer 输出、UI 入口来源等非权威信号推断任务类型。

## 3. 草案条文

### 3.1 D-1：Agent 任务的空判据集不合法

**条文**：当 Task 存在 `actor_kind=agent` 的 active Assignment（或本次操作将建立这样的 Assignment）时，其当前 `contract_rev` 的 `acceptance_criteria` 必须非空且至少一条可判定条目；空判据集一律**拒绝**，不得先落库再标记不合法，不得由内核自动补判据。

**拒绝时点（四个，缺一不可）**：

| # | 时点 | 触发操作 | 拒绝依据 | 拒绝后状态 |
|---|---|---|---|---|
| R1 | 定义 | `captured → defined`（TaskDefined），且同事务内指派 Agent | v1.0 §3.1"指派 Agent 时另须满足 REQ-TC-1" | Task 保持 `captured`；不产生 `TaskDefined` |
| R2 | 指派 | 人类显式指派 Agent，或 PlanChange 的 `add_task`/`reassign` 应用建立 active Agent Assignment | REQ-TC-1（本文前移，见 Q1） | Assignment 不建立；Task 原 lifecycle 不变 |
| R3 | 契约换版 | `ContractUpdated` 新 rev 为空判据集，而当前为 Agent 任务 | REQ-TC-1（本文前移，见 Q1） | 新 rev 不建立；仍按旧 rev 执行/验收 |
| R4 | 派发兜底 | Scheduler 拟创建 `run_kind=executor` 的 Run | REQ-TC-1 原文"否则 Scheduler 不得派发" | 不创建 Run；Task 停在 `defined`；投影原因码 `contract_incomplete` |

说明：

- R1 与 R2 覆盖"先定义后指派"与"定义同时指派"两种顺序；R4 是对历史数据/导入数据的兜底，保证即使 R1–R3 被绕过也不会派发 Agent Run。
- R3 拒绝换版**不影响**既有 Acceptance 的效力（REQ-ACC-1 跨 rev 有效），也不撤回已有 Outcome。
- 拒绝必须是**同步、零事件**的：不产生 `TaskDefined`/`ContractUpdated`/`AssignmentCreated`/`RunCreated`，不产生任何状态变更（与 v1.0 §4"不存在无事件的状态变更"一致，拒绝不构成变更）。

**建议的拒绝方式与错误口径（待裁决 Q2）**：

- 传输层：与既有命令面一致的 `ok:false` + `error` 信封；HTTP `400`（输入契约不满足前置条件，非权限问题）。
- 机器可读口径：`error.code = "bad_request"`（沿用既有 `ERROR_CODES`），`error.detail` 固定字段：

  ```json
  {
    "field": "acceptance_criteria",
    "reason": "empty_for_agent_task",
    "task_id": "<ULID>",
    "contract_rev": 2,
    "actor_kind": "agent"
  }
  ```

- 面向人的 `message` 建议：`Agent 任务的契约必须至少包含一条可判定 acceptance_criteria（REQ-TC-1）`。
- 若 v1.1 决定新增顶层错误码（如 `contract_incomplete`），须在 v1.1 登记并同步扩充错误码封闭集；**v1.0 无 Task 命令级原因码封闭集**（`REQ-PC-3` 的原因码只适用于 PlanChange status），故本文只作建议（Q2）。

**派发兜底的非事件呈现（待裁决 Q3）**：建议仅在投影给出原因码 `contract_incomplete`（与 REQ-SCH-4 的 `no_capable_actor` 同风格、不占 `wait_state`），不产生 Decision；若认为需要人介入补判据，则应产 Decision 并单列条文。

### 3.2 D-2：人工任务的空判据集合法，但 verdict 必须由人显式给出

**条文**：当 Task 无 active Assignment，或 active Assignment 的 `actor_kind=human` 时，其 `contract_rev` 的 `acceptance_criteria` 可以为空（REQ-TC-1"人工执行的 Task 允许仅文本契约"），且契约换版为空不构成拒绝理由。

在此前提下，**v1.1 须显式写死以下验收口径**：

1. **一致性校验不适用于空集**：`criterion_results=[]` 且契约 `acceptance_criteria=[]` 时，REQ-ACC-2 的顶层 verdict 三分支**不予套用**，一致性校验取"不拦截"；覆盖完整性与继承锁定两项校验**真空成立属预期行为**，不产生 `violation`，也不代表"已验证通过"。
2. **内核不得从空集推导 verdict**：不得因"全部 passed"在空集上真空成立而自动生成 `accepted`，不得生成任何无人工提交的 Acceptance。
3. **verdict 必须由人显式提交**：须存在 `AcceptanceRecorded` 事件，且 `acceptor_kind=human`，`verdict` 显式给出；`system` / `agent` 代判一律拒绝入账（空集不存在 `auto` 判据，REQ-ACC-2 的自动验收路径不适用）。
4. **verdict 取值建议限于 `accepted|rejected`**：空集不存在"混合结果"，`partially_accepted` 的待补集为空、语义退化，建议拒绝（Q4）。
5. **未提交 Acceptance 前不得 accepted**：Task 在有 Outcome 后停在 `awaiting_acceptance`（REQ-ACC-3 已有"无有效 Acceptance 且已有 Outcome → `awaiting_acceptance`"），直到人工显式 Acceptance 入账后才按 REQ-ACC-3 重算。
6. **actor 分离仍适用**：REQ-ACC-2"执行该 Run 的 actor 不得担任其 Acceptance 的 acceptor"对人工任务无字面例外；K0 单用户实现以 `self_acceptance` 标记"执行者自验收"（`server/HANDOFF.md` §5、`src/kernel/actor-guard.ts`），该放宽是否在 v1.1 明文写成 `human_light` 例外，列为 Q6，本文不擅自采纳。
7. **建议 `rationale` 必填**（Q5）：空集没有 `criterion_results` 承载判定依据，`rationale` 是唯一可审计的裁决理由。

### 3.3 D-3：非空判据集完全沿用既有 REQ-ACC-2

非空判据集不因本文新增任何校验：一致性三分支、覆盖完整性、继承锁定、actor 分离、REQ-ACC-3 重算均按 v1.0 原样执行。本文只对"空/空"组合补口径，不修改"非空/空"与"非空/非空"的既有行为。

**四种组合的边界表**（便于实现与测试对齐）：

| 契约 `acceptance_criteria` | `criterion_results` | 既有/草案口径 | 结论 |
|---|---|---|---|
| 空 | 空 | 本文 D-1 / D-2 | Agent 任务：契约非法（R1–R4 拒绝）；人工任务：可入账但须人显式 verdict |
| 空 | 非空 | v1.0 未写；建议拒绝（Q7） | `criterion_results` 引用了契约不存在的 `criterion_ref`，建议按覆盖完整性对偶拒绝 |
| 非空 | 空/缺项 | REQ-ACC-2 ① 覆盖完整性 | 缺项拒绝入账（既有） |
| 非空 | 全覆盖 | REQ-ACC-2 三分支 + ②③ | 原样执行（既有） |

### 3.4 D-4：契约换版与空集的交互

- 人工任务：空 → 非空、非空 → 空均允许（文本契约与结构化契约可互转）；换版不回溯作废既有 Acceptance（REQ-ACC-1 跨 rev 有效），除非新 rev 显式 `declares_revalidation=true`。
- Agent 任务：非空 → 空一律拒绝（R3）；空 → 非空是修复方向，允许。
- 已入账的 Acceptance 钉死其 `contract_rev` 与 `subject_outcome_id`，不因换版被改写；需要重验只能走 `declares_revalidation` 或 supersede 路径（REQ-ACC-1/4）。

## 4. 对照小用例（格式对齐 v1.0 §8.2）

命名为 `D1–D7`，**均为草案用例，未冻结**；编号与 v1.0 的 `C1–C6` 不冲突。

- **D1（对照用例，空判据 + Agent 任务 → 定义点拒绝）**：前置条件——Project P；Task T 处于 `captured`、无 active Assignment；人类 actor H 提交"指派 Agent A + 定义契约"（`contract_rev=1`，`acceptance_criteria=[]`，`expected_outputs` 非空）。→ 内核在 `captured → defined` 前校验 REQ-TC-1。断言：拒绝；T 仍 `captured`；事件流零新增（无 `AssignmentCreated` / `TaskDefined` / `ContractUpdated`）；返回 HTTP 400、`error.code=bad_request`、`detail.reason=empty_for_agent_task`。**对照半例**：同一构造把 `acceptance_criteria` 改为 1 条可判定条目 → `TaskDefined` 与 `AssignmentCreated` 均入账，T=`defined`。
- **D2（对照用例，空判据 + Agent 任务 → 契约换版点拒绝）**：前置条件——T 为 Agent 任务（active `Assignment.actor_kind=agent`），`contract_rev=1` 有 1 条判据，Run 已 succeeded、Outcome 已入账，T=`awaiting_acceptance`。→ 提交 `ContractUpdated` 使 `rev=2` 的 `acceptance_criteria=[]`。断言：拒绝；`rev=2` 不存在；T 仍按 `rev=1` 验收；既有 Acceptance 不被撤回；零事件。
- **D3（对照用例，空判据 + Agent 任务 → 派发兜底不派发）**：前置条件——库内已存在 Agent 任务且当前契约空判据（模拟导入/历史数据绕过 R1–R3）。→ Scheduler 执行 ready 判定并拟派发 `run_kind=executor`。断言：不创建 Run（无 `RunCreated` / `RunQueued` / `RunLeased`）；Task 停在 `defined`；投影原因码 `contract_incomplete`；不静默派发、不自动补判据。
- **D4（对照用例，空判据 + 人工任务 → 可创建、可执行，但不得自动 accepted）**：前置条件——T 处于 `captured`，指派人类 H（`actor_kind=human`），`contract_rev=1` 的 `acceptance_criteria=[]`。→ `TaskDefined` → ready → `human_light` Run `created/running` → Feedback 入账 → Outcome 入账。断言：全过程成功；T=`awaiting_acceptance`；事件流无 `AcceptanceRecorded`；T 不为 `accepted`——即使"全部 passed"在空集上真空成立，也不得推导 `accepted`。
- **D5（对照用例，空判据 + 人工任务 + system/agent 代判 → 拒绝）**：前置条件——承接 D4 至 `awaiting_acceptance`。→ 以 `actor_kind=system`（或 `agent`）提交 `AcceptanceRecorded`（`verdict=accepted`，`criterion_results=[]`）。断言：拒绝入账、零事件；理由为"空集无 `auto` 判据，REQ-ACC-2 自动验收不适用，verdict 须由人显式给出"；T 仍 `awaiting_acceptance`。
- **D6（对照用例，空判据 + 人工任务 + 人显式 verdict → 入账并重算）**：前置条件——承接 D4；人类 H2 提交 `AcceptanceRecorded`（`verdict=accepted`，`criterion_results=[]`，`rationale` 非空）。断言：入账；一致性校验不拦截；覆盖完整性与继承锁定真空成立且不产生 `violation`；T=`accepted`，并按 INV-11 同事务收尾 WaitCondition。**对照半例**：同一构造 `verdict=rejected` → 入账，T=`defined`（REQ-ACC-3 rejected 分支）。**边界半例（待裁决 Q4）**：`verdict=partially_accepted` → 建议拒绝（待补集为空、非"混合"）。
- **D7（对照用例，非空判据 → 走既有 REQ-ACC-2）**：前置条件——契约有 `c1,c2,c3` 三条判据。→ 提交 `criterion_results` 为 `c1=passed, c2=failed, c3=not_applicable`、顶层 `verdict=partially_accepted`。断言：入账；T 停在 `awaiting_acceptance`，待补集 = `{c2}`（REQ-ACC-3）。**对照半例一**：顶层 `verdict=accepted` 但 `c2=failed` → 一致性不符，不入账。**对照半例二**：缺 `c3` → 覆盖完整性不符，不入账（v1.0 既有）。

## 5. 待裁决

> 以下为草案拿不准处，均需在 v1.1 评审中裁决；未裁决前不写入实现判据。

- **Q1：拒绝点是否前移？** v1.0 只写死两处（§3.1 `captured → defined` 指派 Agent 时、REQ-TC-1 的 Scheduler 不得派发）。本文把校验前移到**指派点（R2）与契约换版点（R3）**，属收紧而非放宽；需裁决是否采纳，以及 R2 在 PlanChange `add_task`/`reassign` 应用时是否同口径拒绝整个 Change（按 REQ-PC-2 原子性，建议整单不应用）。
- **Q2：错误码口径。** v1.0 无 Task 命令级原因码封闭集；建议沿用 HTTP 400 + `code=bad_request` + `detail.reason=empty_for_agent_task`，不新增顶层错误码。若需新增，须在 v1.1 登记并同步错误码封闭集。
- **Q3：派发兜底是否产 Decision？** 建议只给投影原因码 `contract_incomplete`（对齐 `no_capable_actor` 的处理），不产 Decision；若要求人补判据，则需写死 Decision 的 `subject_ref` 与唤醒条件。
- **Q4：空集下的 `partially_accepted` 是否允许？** 建议拒绝：空集无"混合"结果，待补集为空，`partially_accepted` 停在 `awaiting_acceptance` 会形成无可执行补集的状态。
- **Q5：空集下 `rationale` 是否必填？** 建议必填（唯一裁决依据）；v1.0 未对 `rationale` 设必填约束，需 v1.1 明文。
- **Q6：人工任务是否允许"执行者自验收"？** v1.0 REQ-ACC-2 字面为"执行该 Run 的 actor 不得担任其 Acceptance 的 acceptor"，对 `human_light` 无例外；K0 单用户实现以 `self_acceptance` 标记放行（`server/HANDOFF.md`、`src/kernel/actor-guard.ts`）。需裁决：在 v1.1 明文写 `human_light` 例外，还是按 v1.0 字面收紧实现。
- **Q7：`expected_outputs` 与"多余 `criterion_ref`"。** ① REQ-TC-1 同句要求 Agent 任务有 `expected_outputs`，本文只裁 `acceptance_criteria`，是否同单加严待裁决；② 契约空但 `criterion_results` 非空（孤儿判据）v1.0 未禁止，建议按覆盖完整性对偶拒绝，需裁决是否入条文。
- **Q8：`TaskCaptured` 是否也拒绝空判据？** 本文建议**不拒绝**：Capture 要求 1 次请求内返回"已记录"并以异步事件补齐结构化（REQ-PJ-3），且捕获时指派对象未知；若在捕获点强制判据，将与该条及 D10/OQ-01 的"游离 Feedback → TaskCaptured"落点冲突。
